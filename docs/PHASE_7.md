# Phase 7: onboarding, settings, accessibility and performance

Branch: `phase-7-accessibility-polish`, from Phase 6 merge `37fc6a3`. This phase implements the guided first-use flow and the code audit. **The full VoiceOver/TalkBack run and phone performance acceptance remain pending.** No camera, screen reader, hardware key, audio or haptic phone result is claimed from cloud tests.

## First use and replay

Welcome offers Learn the controls, Listen again and Use camera now. The quick path retains the existing spoken permission flow on Camera. The guided path has four short, visible and spoken lessons covering camera zones, framing tones/haptics, guidance modes and recording/review/sharing. Lessons describe the supported face target and the current Subject → Settings route, rather than promising unavailable body/object tracking or an extra camera control.

Lessons lead to Camera, Microphone, Spoken commands and add-only Photos access, **one page at a time**. Each page explains the purpose, current state and consequences of denial. Allow access first speaks the explanation, then invokes the OS. Nothing is requested automatically by these pages. Skip this request leaves existing OS permissions unchanged. Open settings and Listen again remain available; a failure does not trap the user. Completing access review records one local settings flag so subsequent automatic camera/Photos flows do not re-prompt skipped access, including after relaunch. Explicit requests in App access or Review's Save can retry. Existing installs retain their first-use behavior until they review access; missing stored fields receive their defaults.

On iOS, Speech asks for speech-recognizer permission separately, so it does not silently re-request a denied microphone. Android explains that spoken commands need microphone access first. All access values are permission states, not a guarantee that a particular speech service/language pack is installed. Live-command Apple/Google fallback (D19) and local-only saved-video analysis are unchanged.

Explanations can be cancelled on navigation/backgrounding. They cannot open a delayed permission dialog after cancellation. A dialog already presented belongs to the OS; its promise is shared across app re-entry, preventing duplicate requests. A still-visible page rechecks its final status after returning. No late result advances a step or acts on another screen.

After access review, Practice shows a local camera preview **only if camera access was allowed**. It has no recording/audio/frame-analysis outputs and never creates a recorder or file. Button/volume actions change local practice state and confirm with a short cue and vibration. Apple's existing capture-button module needs a running camera session, so iOS volume practice enables only after the preview starts, and only on supported iOS versions. Android can practise volume keys without a preview. Unsupported devices, denied camera access or preview errors retain the screen button and Continue. Practice closes its preview and key subscription on leaving/backgrounding. The real Camera still requires a separate explicit Record action.

Replay tutorial from Settings → More keeps sound, feedback, models and any existing recording. Finish returns to More; it does not reset settings or create a replacement clip. An unfinished first-use flow remains incomplete until the user finishes Practice or chooses the quick Camera path.

## Settings and accessibility changes

- More now has App access alongside models, tutorial and app information. App access lists all four permissions and refreshes after phone settings changes.
- Camera and recording links to Framing preferences. That page exposes existing automatic lens switching and a 60–90% safe zone, in 5% steps; 80% remains the default. Settings keep the four-control limit.
- Switches/adjustables give spoken confirmation through the cue engine after a user's change, using the current speech speed/volume. Native screen reader state/value feedback is not duplicated. Double tap and increment/decrement actions remain available.
- Shared buttons, switches and adjustables have keyboard focus treatment and at least 60-point dimensions. Long button text wraps; switches stack label/state at large text sizes. Disabled controls keep full text contrast, with dashed borders and disabled semantics.
- Standard headers focus the native accessible heading after navigation, with an announcement fallback. Old per-page duplicate announcements were removed. Tutorials/access explanations use their own cancellable narration; Review speaks its title with the recording summary. Playback retains heading focus while its speech lease protects recorded audio.
- All navigation stacks honor the OS Reduce Motion setting, including changes while the app is open. Text uses the existing scalable system-font tokens without a font-scale cap.
- At font scale above 1.4 or screen height below 520 points, Camera puts the **same** actions in a scrollable list over the live preview. This avoids fixed corner controls overlapping at large text/short landscape sizes. It announces the layout change, retains status tap/Record/Flip/Mode/Subject and the contextual scan/scene action, and still has at most six controls. Normal portrait keeps its corner layout. Settings remains reachable through Subject (D31).
- Version is an accessible button for the existing hidden five-activation diagnostics. Subject/debug changes and external-link failures now receive cue-engine feedback.

See [ACCESSIBILITY_AUDIT.md](ACCESSIBILITY_AUDIT.md) for the evidence and remaining device checks.

## Performance pass

Framing still consumes every fresh detector callback for tones, automatic zoom and recording statistics. React receives semantic guidance changes; debug box drawing is capped at 4 Hz, and the guidance-rate display updates only when debug is enabled. A regression feeds 100 detector packets, verifies all 100 observations and permits at most four additional React renders for unchanged guidance. This is a simulated-render regression, **not a phone frame-rate benchmark**.

Identical feedback observations reuse the existing UI state while every observation still updates recording statistics and cue dwell logic. The feedback watchdog does not run while disabled. Background expiry publishes a stale/empty state once, instead of replacing an empty array every 500 ms indefinitely. Recording cue policy is applied synchronously before microphone startup, without waiting for a React effect; permission explanations stop when capture starts. This preserves the earphones/pause policy for startup confirmations too. Existing downsampling, frame disposal, stale-generation guards, active-screen checks and the single Android analysis-output limit remain intact. Practice adds a preview, not another analysis pipeline.

Debug distinguishes guidance updates from preview frame rate; Framing timing is not shown as a measurement of other modes. No evidence in this cloud session demonstrates 30 fps preview, battery/thermal behavior or the Phase 5 five-second VLM target. Those require the phone run below.

## Phone acceptance

Install this phase's PR APK/development build, not an older main release. Record commit, phone, OS, camera facing/orientation, reader and cue settings. Repeat the full journey **without sighted help**, once with VoiceOver on iPhone and once with TalkBack on Android; also repeat core controls with the reader off. Use the Phase 2–6 feature scripts for detailed camera/lighting/feedback/model calibration.

1. Fresh first use: hear Welcome, navigate the four lessons with Next/Back and Listen again, and skip remaining lessons once. Instructions must be readable and spoken through a single voice. Navigate away/background during a lesson: no old narration should continue or restart after a newer page. An early manual Listen again must not be followed by a duplicate automatic reading.
2. Access pages: allow, deny, permanently deny and skip each permission in separate test runs. Only Allow may cause the explained OS request. iOS Speech must not re-request a denied microphone; Android must explain that dependency. Return from phone settings and verify the displayed final state. Leave/background during the explanation: no delayed prompt. Returning from an actual OS dialog must not produce a duplicate prompt or a stuck busy state.
3. Complete access review with permissions skipped, finish Practice, close/relaunch Lumi and record where possible. No skipped permission should be automatically re-requested. Photos denial must leave the app copy shareable; explicit Save/App access can retry after granting permission. The quick Use camera now path must still explain any needed requests sequentially.
4. Practice with camera allowed: expect an inline preview, camera privacy indicator, no microphone capture/indicator and no saved recording. Use the screen button twice and, on a supported phone, a volume key twice. Expect practice-start/stop cues and one vibration, with no change to system recording state or Photos. On iPhone, volume capture starts only after the preview runs. Check iOS 16.4–17.1 fallback, denied camera access, TalkBack volume shortcuts and a preview failure: the screen button and Continue must remain usable. Leave/background and verify key handling/preview stops.
5. Finish Practice: expect Camera with no recording running, no camera-in-use error and normal audio on the next real recording. Replay from More and finish again: return to More with custom speed/volume, feedback choices, model installation and the previous clip preserved.
6. Find Settings via Subject. Change every switch/adjustable by double tap and screen reader adjustment actions; hear one state/value confirmation. Test both numeric endpoints, cycle/wrap, persistence after relaunch, Framing safe-zone changes and separate feedback toggles. Reader off: speed/volume confirmation should use the new setting. Reader on: no overlapping Lumi speech and native value announcement.
7. With the largest text/display size, test small portrait, both landscape directions and iPad. Every label/value must remain readable, controls reachable, and camera controls scroll without overlapping actions. Scrolling and reader focus must reach Record, status, Mode, its scan/scene action, Subject and Flip. Rotating/changing font size must not interrupt a recording or attach a second analysis output. Check first/last scroll items and safe-area edges.
8. Check heading focus and Back on every settings/model/tutorial/review/playback page, including return from OS sheets. Focus must not jump back to an old heading after leaving it. Check disabled controls, progress/error states, saved/unsaved Review and model download/cancel states. Use an external keyboard if available: each app control needs a visible focus indicator and activation without touch.
9. Enable Reduce Motion before launch, then toggle it while open. Expect no stack fade when enabled. Test light/dark/high-contrast modes and reader speaking rates from slow to fast. Native reader announcements, help and live commands must not talk over each other or cause actions from UI speech. Saved video command phrases must remain inert during playback/analysis.
10. Without sighted help: set Face, follow framing tones in E1, check E2 darkness/E3 backlight/E4 side light, return to a good setup, record with audio, stop, hear Review metrics, Play/Pause, optionally analyse saved voice, Save and Share. Choose YouTube if offered and complete its posting flow. Record every point requiring help, including OS/receiving-app screens; do not mark the phase accepted if any core step needs sighted assistance.
11. Performance on iPhone 12/Galaxy A54 class phones: run each mode for two minutes on both cameras, then leave/background for a minute. Look for stale cues, preview hitches, missing audio, delayed buttons, heat and battery use; disabled/background analysis must stop. Repeat with the largest text and reader enabled. Hidden debug in Framing should show guidance cadence and boxes; it must not claim preview fps. Use device profiling to establish the 30 fps preview target, and record actual results rather than substituting unit-test timing. Existing model benchmarks remain the separate Phase 5 acceptance check.

Keep the phase PR unmerged until native CI and these owner phone checks pass.
